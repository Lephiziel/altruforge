### Effective test profile

This disposable profile was loaded by the trusted Codex client from a temporary `CODEX_HOME/config.toml`; it did not alter the user's normal Codex config:

```toml
default_permissions = "workspace-only"

[permissions.workspace-only]
extends = ":workspace"

[permissions.workspace-only.filesystem]
":root" = "deny"
":minimal" = "read"

[permissions.workspace-only.filesystem.":workspace_roots"]
"." = "write"

[shell_environment_policy]
inherit = "core"
ignore_default_excludes = false
```

The profile gives sandboxed commands workspace writes and minimal runtime reads, denies other host filesystem reads, and uses the documented `core` environment inheritance baseline with automatic secret-name exclusions. The test did not claim that arbitrary inherited environment is safe under the default `workspace-write` profile.

The committed probe [`scripts/mvp01-boundary-probe.py`](../../scripts/mvp01-boundary-probe.py) checks two synthetic files (`credential.txt` and `personal.txt`) by reading at most one byte and reports only access status. It checks `MVP01_SENTINEL` presence in the command and a child process without printing the value. The synthetic canary directory was created under the host home with mode `0700`; its files used mode `0600`. The directory and files were removed after the test.

## ADR outcome

ADR 0003 remains **evidence-gated**. The default Codex `workspace-write` mode failed the sentinel test: host files and an inherited marker were readable by project commands and children. A documented Codex `workspace-only` profile with root-read denial and `core` environment inheritance passed those Linux checks through both the native sandbox command and a non-interactive `codex exec` turn. This is a concrete supported candidate, but not accepted for MVP: Windows' unelevated route refused the strict profile, while its elevated helper could not start the thread with the same root-read denial. The denial was not weakened to bypass that failure. macOS and the production runtime are also untested. Supplementary Docker isolation passed but is not connected to Codex tool execution. Do not claim this boundary as implemented or use unrestricted host execution as a fallback.

## Limitations and follow-up

This evidence does not complete MVP-01. A follow-up must determine whether a documented Windows configuration can enforce the required root-read denial with the elevated sandbox (without broadening project access), integrate the supported permission profile with the app-server adapter (or another documented interface), ensure every project command and child uses the enforced profile, and implement a supervisor-owned durable checkpoint. Capture the app-server protocol version and test the full scenario on Windows, macOS, and Linux, including Unicode/spaced paths, cancellation, explicit recovery, and the exact resolved execution image. Until then all platform gates and dependent claims remain blocked.
